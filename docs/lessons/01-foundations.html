Lesson 1/ Module 1/ ~50 min

Foundations

Define the agent's job precisely enough that "it failed" becomes a decidable claim rather than an opinion.

01 Objective

By the end you can take any run of an agent and say, without argument, whether it succeeded, because you will have written down what success means at three separate levels and seen why the top level alone is not enough.

02 The failure this prevents

A team ships an agent, someone says it feels worse this week, and nobody can settle it. There is no shared definition of a correct run, so every debate collapses into taste. Eventually somebody proposes "let's measure user satisfaction", which is unfalsifiable on a sample of forty conversations, and the argument continues.

The specific version of this failure, the one you will see in the lab, is subtler and more common. A team does define success, but defines it only at the level of the final answer. Their eval then reports 94 percent and they believe it. Meanwhile the agent is reaching for actions it is not allowed to take, being blocked by code, and recovering. The number is real. It is also measuring the wrong thing, and it will keep looking healthy right up until someone removes the thing that was quietly catching the mistakes.

03 Concepts
Outcome-level success
Did the user end up in the correct end state? For a return request: was the decision right, was the amount right, was the customer told the truth. Judged from the final response alone.
Trajectory-level success
Did the agent take an acceptable path? Did it consult the authoritative source instead of recalling policy from memory, respect the order in which rules apply, and avoid actions it had no business attempting. Judged from the sequence of steps.
Step-level success
Was each individual action valid on its own terms? Permitted by role and tier, well-formed arguments, returned without error. Judged one span at a time.
The Three Gulfs
Comprehension (you do not know what your system is actually doing), specification (you cannot state what it should do), and generalization (it does the right thing here and not there). This course maps them onto three verbs: analyze, measure, improve. This lesson is entirely about the second gulf, because you cannot close the other two while the specification is still vague.
Progressive tool disclosure
Offering a model only the tools its role can actually use, rather than the full set plus an instruction to behave. The analyst in this repository is never shown issue_refund. A tool that is not on the menu cannot be ordered by mistake.

Why three levels and not one

The levels are independent. A run can pass at the outcome level and fail at the step level, or the exact reverse. The lab gives you one of each and asks you to tell them apart. If they were not independent, one number would do and this lesson would not exist.

04 Mental model

A run is a tree, and each level reads a different part of it.

session ─────────────────────────────── OUTCOME   final response vs ground truth
 ├── model_call:0
 ├── tool:lookup_order            ok  ─┐
 ├── model_call:1                      │
 ├── tool:check_return_eligibility ok  ├─ TRAJECTORY  was this the right path?
 ├── model_call:2                      │
 ├── tool:create_return_label  DENIED ─┘
 │                                 └──── STEP     was this one action valid?
 ├── model_call:3
 ├── tool:create_return_label     ok
 └── model_call:4

Read only the top line and the denial in the middle is invisible. Read only the denials and you cannot tell whether the customer was helped. Both readings are incomplete and both are routinely shipped as "the eval".

05 Browser lab
Lab 1/no install

Three-level success writer

Three real runs of the Wayfarer agent. For each one you judge pass or fail at all three levels before seeing the answer. One run passes everywhere, one is right for the wrong reasons, and one is quietly wrong in a way no permission check will ever catch.

Open the lab

06 Local lab

Break the permission layer on purpose, and watch it not break.

# from the repository root, in a virtualenv
make check                     # all five gates, no API key needed
python agent/support_agent.py --selftest

The selftest drives the real control loop with a scripted client, so it needs no API key. Read what it asserts, then go break one of them deliberately: open data/world/facts.yaml, raise refund_auto_approve_limit_cents from 20000 to 500000, and run make check again.

Two different gates should fail, and they should disagree with each other in a specific way. Read both messages. That disagreement is the entire argument for keeping ground truth and enforcement in separate files. Then put the value back.

Expected output

make check ends with all gates passed. The selftest prints a list of ok lines and then agent selftest passed. Anything else means stop and read, because everything in later lessons assumes these invariants hold.

07 Traps
  • Check whether your success criterion can be evaluated by someone who was not there. "The agent was helpful" cannot. "The refund equals the amount rules.py computes for that line" can, and two people will agree on it without a meeting.
  • Check whether your permission layer is being mistaken for an eval. A gate bounds what the agent may do. It says nothing about whether what it did was right, and it usually only guards one direction. In this repository the gate blocks refunds that are too large and permits refunds that are too small, because only one of those costs the company money.
  • Check that the safe action is actually reachable. Escalation to a human is the designated fallback for every case the agent cannot handle. In this repository it was silently unreachable for both roles, because an unclassified tool defaults to the highest risk tier and the highest tier always requires a human. Two correct-looking assertions passed the whole time. Nothing asserted that the escape hatch opens.
  • Check whether you are agentic where you should be deterministic. Deciding whether a return is within its window is arithmetic over two dates. Handing that to a model buys nothing and introduces a failure mode. Ask the model to converse; ask code to decide.
08 Self-check

You are done with this lesson when you can answer these without looking:

  • Give an example of a run that passes at the outcome level and fails at the step level.
  • Give an example of the reverse.
  • Why is "did the tool call return an error" a poor definition of step-level success?
  • Your agent refunds a customer 30 percent less than policy entitles them to, and every permission check passes. Which level catches it, and what does the check compare against?
  • Name one decision in this agent that should not be agentic, and say what it costs you if it is.
