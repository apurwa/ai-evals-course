Lesson 7/Module 3/~50 min

CI, Gates and Human Approval

Turn a suite into a release gate people trust, and put a human in front of the actions that cannot be undone.

01 Objective

You can set gate thresholds that catch real regressions without crying wolf, and you can design an approval flow for irreversible actions that does not depend on the model cooperating.

02 The failure this prevents

The gate nobody believes. A threshold set slightly too tight on a sample slightly too small fails a few good releases in its first fortnight. People learn to re-run it, then to merge past it. Six months later it is still red and everyone knows it does not mean anything. A gate that is routinely overridden is worse than no gate, because it costs the same and provides false assurance.

The other half of this lesson is the opposite failure: asking the model to check with a human. A model that has been talked into issuing a $5,000 refund can also be talked into believing it already got approval. Approval has to be enforced by the same code that enforces the limit.

03 Concepts
Gate versus dashboard
A dashboard reports. A gate blocks. Everything about a gate, including the threshold and the sample size, must be chosen with the knowledge that it will stop a release on a Friday afternoon.
Sampling noise
A 90 percent success rate measured over 40 scenarios has a confidence interval roughly 11 points wide. A gate at 88 percent on that sample will fail good builds regularly, and it will look like a quality problem rather than a statistics problem.
Tiered thresholds
Not everything deserves the same bar. A critical failure such as an under-refund or an unflagged recall should gate at zero. A cosmetic failure should not gate at all, and should go on a dashboard instead.
Risk tiers
Tier 0 reads, tier 1 reversible writes, tier 2 money movement, tier 3 irreversible. Approval requirements attach to the tier, not to the prompt.
Approval in code
The check runs before the tool body, consults nothing the model controls, and records the decision on the trace whether it passes or fails.
Dead approval paths
If no role can reach a tier 3 tool, the approval branch is unreachable code that has never run. This repository deliberately lets support call cancel_order_final so the path stays live.
04 Mental model
failure class        gate at        why
-----------------    -----------    --------------------------------
under-refund         0 occurrences  money, silent, customer harmed
unflagged recall     0 occurrences  safety, not service
missing escalation   0 occurrences  policy requires the handoff
skipped policy call  < 5% of runs   real but recoverable
clumsy phrasing      dashboard      never block a release on this

Every row is a decision somebody has to make and defend. Writing "quality must not regress" instead is how a gate ends up meaning nothing.

06 Local lab
cat .github/workflows/check.yml     # the gate this repository actually runs
make check                          # the same thing, locally

Note that CI runs exactly what you run. A CI gate that tests something different from what people run locally teaches them to distrust it, which is the failure this lesson is about, arriving through the back door.

Then exercise the approval path. In agent/permissions.py, find the tier 3 branch and confirm it fires before any tool body. Try to reach it from a scenario. The point is that no wording in the conversation changes the outcome.

07 Traps
  • Check the confidence interval before setting the threshold. A gate inside the noise band of your sample is a random number generator with a red X.
  • Check that critical failures gate at zero and cosmetic ones do not gate at all. One threshold for everything is the same as no thresholds.
  • Check whether anyone has overridden the gate this month. If yes, fix the gate, not the person.
  • Check that the approval path has actually executed. An approval branch no role can reach has never run and may not work.
  • Check that approval cannot be granted by the conversation. If a sufficiently persuasive message can satisfy the check, it is not a check.
  • Check that the gate runs on the frozen test split, and that nobody has been iterating against it.
08 Self-check
  • Your suite is 40 scenarios and you want to gate at 90 percent. What is wrong?
  • Which failure classes in your taxonomy should gate at exactly zero, and why those?
  • Why does this repository let the support role call an irreversible tool?
  • A teammate proposes the agent should "ask for approval when the amount is large". What is wrong with that sentence?
