Lesson 8/Module 4/~55 min

Safety and Red-Teaming

Prompt injection has no reliable detector, so authorization has to hold in code that the model cannot reach or argue with.

01 Objective

You can design an authorization boundary that survives a fully compromised model, and you can tell the difference between a control and a mitigation.

02 The failure this prevents

Defending in the prompt. "Never issue a refund above $200 without approval" is a sentence in a document that an attacker also gets to write in. Every prompt-level defence is negotiable, because the attacker's text and your text arrive at the model through the same channel and have the same status.

The second failure is subtler and more common in mature teams: building an injection classifier and treating it as the boundary. Classifiers help. They also have a false negative rate, and the boundary needs to hold on the day one gets through, which is the only day it matters.

03 Concepts
Prompt injection
Instructions supplied through data the model reads, which the model cannot reliably distinguish from instructions supplied by you. Not a bug to be patched. A structural property of putting text and commands in the same channel.
Control versus mitigation
A control holds regardless of what the model does. A mitigation reduces how often the model is asked to do the wrong thing. Both are worth having. Only one belongs on the boundary.
The compromised-model assumption
Design as though the injection has already worked and the model is now cooperating with the attacker. If your system is still safe under that assumption, it is safe. If the answer depends on the model behaving, you do not have a boundary.
Gate arguments from the database
The permission layer in this repository never reads the hazmat flag from the model's tool arguments. It reads it from the database. Otherwise a compromised model would simply say the item is not hazmat.
Confused deputy
The agent has authority the user does not. Any path where user text steers that authority is the vulnerability, and role separation is the answer.
OWASP Top 10 for Agentic Applications
Worth reading end to end. The categories most relevant here are excessive agency, improper output handling, and privilege escalation through tools.

The gap this lesson does not paper over

The permission layer in this repository blocks refunds that are too large and permits refunds that are too small, because every rule it enforces is about the company's exposure. That is a real, unfixed asymmetry, and the lab shows it rather than leaving it out. A boundary that protects only one party is doing half a job, and knowing which half is the difference between a security posture and a security feeling.

05 Browser lab
Lab 8/real verdicts

Attack console

Fifteen attacks, each assuming the injection already worked and the model is fully cooperating. The verdicts are not simulated: every one was produced by running the real agent/permissions.py and recording what it returned. Fourteen are refused. Find the one that is not, and work out why that is the honest answer rather than a bug.

Open the lab

06 Local lab
python scripts/build_redteam.py       # fires all 15 at the real gate
python scripts/check_permissions.py   # 104-case sweep plus assertions

Then try to break it. Open agent/toolset.py and find where ToolRegistry.call derives is_hazmat. Change it to read the value from the model's arguments instead of from the database, and re-run build_redteam.py.

The hazmat attack should now succeed, and the script should fail the build with a security regression message. That is the difference between reading a gate argument from the world and reading it from the thing you are defending against. Put it back.

07 Traps
  • Check whether any gate argument comes from the model. If one does, that gate is advisory.
  • Check that denials are recorded. A trace that logs only successes cannot tell a blocked attack from an absent one, so you will never know you are under attack.
  • Check what happens on the day the injection classifier misses. If the answer is "we lose", the classifier was load-bearing and should not have been.
  • Check the unknown-tool default. Deny by default, loudly. This repository had a real bug where the safe action defaulted into the highest tier and became unreachable.
  • Check who the boundary protects. Ours protects the company. Ask explicitly whether the customer needs one too, and write down the answer either way.
  • Check that red-teaming is repeatable. A one-off afternoon of creative attacks is a workshop. A committed attack suite that runs in CI is a control.
08 Self-check
  • Why can a prompt not enforce a refund limit?
  • Your gate reads is_final_sale from the tool arguments. What is the attack?
  • Which of the fifteen attacks succeeds, and why is that not a bug in the gate?
  • What is the difference between a control and a mitigation, and where does an injection classifier belong?
